# Assumptions and security boundary

- UUID identifiers are generated by PostgreSQL; UUID inputs are canonicalized to lower case. Missing UUIDs return 404; malformed UUIDs return 400.
- Monetary inputs accept decimal **strings or finite JSON numbers** and normalize to two-place decimal strings. Numeric inputs must not exceed `Number.MAX_SAFE_INTEGER`; use strings for large exact values because JSON numbers are parsed as JavaScript floating point. Fractional cents are rejected rather than rounded. Decimal strings accept integers and one/two fractional digits, without signs, leading zeros (except `0.x`), whitespace, commas, or exponents. JSON numeric notation is normalized after parsing. Values must be positive and <= `9999999999999999.99`. PostgreSQL NUMERIC(18,2) arithmetic returns two fractional digits. All balance arithmetic uses PostgreSQL; no float parser override is used. Numeric input is converted using its decimal representation, without `toFixed` rounding.
- Account names trim surrounding whitespace and allow 1–200 characters. Clients cannot set ID, timestamp or balance. PostgreSQL timestamps use `clock_timestamp()` so long transactions do not predate later actual inserts.
- All user-supplied text rejects NUL characters and unpaired Unicode surrogates before database access. Valid Unicode surrogate pairs are preserved; invalid strings must never collapse onto another reference during UTF-8 encoding.
- Description is optional in posting requests and limited to 2,000 characters. A supplied nonblank description is preserved. Missing, empty or whitespace-only descriptions become `Credit transaction` or `Debit transaction`. Transfer postings receive `Transfer to <destination name>` and `Transfer from <source name>` using names read while the accounts are locked. Explicit JSON null is rejected.
- Fresh databases require a nonblank description on every ledger row through a validated constraint in the initial schema. Older installations can retain immutable null/blank historical descriptions; their existing NOT VALID constraint still enforces new inserts. The submission migrations target a fresh database; no historical backfill or database reset runs at startup. Existing installations retain their data and migration history; do not replay the consolidated initial migration over them.
- References are 1–200 characters, must not be all whitespace, and are preserved exactly, including case and surrounding spaces. Uniqueness is `(account_id, reference_id)`. The `transfer/` prefix is reserved for generated transfer postings.
- Duplicate requests return 409 with the original transaction in `error.details`, even if the submitted amount/type differs. Duplicate checks precede insufficient-funds checks.
- Account balance is a stored projection updated only in the same SQL transaction as the ledger entry through the API. Reconciliation is tested rather than automatically repairing data.
- Mutation transactions use READ COMMITTED and explicit account `FOR UPDATE` locks. API writers follow this locking protocol. PostgreSQL uniqueness/check/FK constraints complement service rules.
- History defaults to page 1 and limit 20, maximum limit 100. Page is bounded to 2,147,483,647. Sorting is `created_at DESC, id DESC`. Empty histories have zero total pages. Account existence, count and page queries share one REPEATABLE READ READ ONLY transaction. Separate page requests can observe newer committed data. Large offsets are intentionally simple for this assessment.
- Ledger rows and transfer metadata reject UPDATE/DELETE through database triggers; the API exposes no mutation endpoints. A privileged owner can alter/disable triggers or issue TRUNCATE. These protections do not defend against an administrator.
- The `ledger` schema is private to the backend; it must not be added to Supabase Data API exposed schemas. PUBLIC receives no access. The migration owner is trusted. Runtime credentials should receive only the grants shown in the README; they must not own the tables or be used in a browser.
- Direct remote PostgreSQL connections always verify TLS and hostname using Node trust roots or `DB_SSL_CA_FILE`. Local loopback uses plaintext unless a CA is configured. URL query overrides (including SSL options) are rejected to prevent node-postgres from overriding verified TLS. Copy provider URLs without TLS query options and configure the CA explicitly.
- Checked-out clients have an error listener throughout each transaction. Transport errors abort the operation and discard the connection without crashing the process; the pool resumes serving requests on replacement connections.
- Startup and readiness verify schema access, required enforced integrity constraints and enabled immutability triggers rather than relying on provider-specific migration bookkeeping.
- Commit network failure can leave an unknown outcome. There are no automatic write retries. Reconcile using the original reference by resubmitting: 409 confirms an existing transaction/transfer; a successful new post only occurs if no original posting committed. History can also locate original references.
- Transfer idempotency is `(from_account_id, reference_id)`; references may repeat across different sources and are independent of standalone posting references. One immutable transfer metadata row links exactly one generated debit and one credit from the service. Accounts are locked sequentially in canonical UUID order to prevent opposing-transfer deadlocks. A failure rolls back metadata, both entries and both balances.
- Tests create a new randomly named database; cleanup requires matching generated name, database owner and unique ownership marker. An external test URL requires explicit opt-in and CREATE DATABASE privilege; the original database is never migrated or cleaned. Default tests launch real PostgreSQL 17 in a temporary cluster.
- Verification covers local PostgreSQL and the documented local Supabase workflow. Hosted networking, TLS, project grants and remote migration application need verification in the target project. No remote deployment is performed.
- **Authentication and authorization are outside the scope of this assessment. The API is not suitable for handling real customer funds without additional access controls and operational protections.**
